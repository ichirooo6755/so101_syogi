目視所見から始まり、評価指標のバグ、物理モデルの不整合、そしてハードウェアの
構造的限界まで辿った一連の作業。**個別の結論は各ドキュメントにあるので、
ここには「何をどう疑って、何が外れたか」を残す。**

## 2. 見つけた不具合

### 2.1 幅の詳細評価が一度も動いていなかった

`evaluate_width_profile` が **89 回呼ばれて 89 回とも ValueError**。実測は制御
ステップ単位（1 画 100-190 点）、目標はウェイポイント単位（20-28 点）で長さが
構造的に一致しない。`try/except` で握り潰され、フォールバックが全項目に同じ値を
入れるため `line_width` が粗い単一指標に退化していた。

**テストは関数を直接呼ぶので通っていた。** 統合部分だけが壊れていた典型。

修正後に初めて内訳が見え、払いの taper が 20.99 と壊滅的なことが分かった。
→ `2026-08-20-width-metric-bug.md`

### 2.2 起筆の保持点が全て同一座標だった

三折法の「トン」が出ないのは、起筆の保持 8 点がすべて同じ XY・Z で、到達判定の
Z 許容 1.2mm の内側にいる限り 8 点とも即座に消費されるため。**穂が沈む時間が
物理的に存在しなかった。**
→ `2026-08-20-sansetsu-diagnosis.md`

### 2.3 紙が硬すぎて筆を抜けなかった

払いの末端で穂先は 0.164mm しか食い込んでいないのに接触力 0.474N が残り、
`1-exp(-F/1.5)` が筆圧 0.27 を返す。計画の目標圧 0.02 に必要な力は 0.034N で
**14 倍の乖離**。`solref` 既定 0.02 では「筆を浮かせながら引く」が成立しない。
→ `2026-08-21-paper-contact-stiffness.md`

### 2.4 墨が楕円のスタンプだった

`radius_squared = (along/major)² + (across/minor)²` は完全な楕円で、`angle` は
進行方向。**楕円をいくら並べても端は必ず丸くなり、起筆の三角は原理的に作れない。**
穂の傾き `roll` も技法情報も `deposit` へ渡っていたのに使われず捨てられていた。
→ `2026-08-21-brush-footprint-and-paper.md`

## 3. 外した仮説の記録

**当たった仮説より、外した仮説のほうが情報量が多い。** 同じ轍を踏まないために残す。

### 3.1 払いが細まらない原因（5 連続で外した）

| 仮説 | 検証 | 結果 |
|---|---|---|
| 引き上げ上限が足りない | 4→22mm | 払い taper 11.10→11.59、全指標悪化 |
| 穂が横に寝すぎ | 曲がり 14.3→8.1mm | **Z 誤差 0.856→0.903 と不変** |
| 筆圧プロファイルが悪い | 全体 0.55 倍 | taper +1.9 だが lw 88.96→82.42 と崩壊 |
| サーボゲイン不足 | kp/kv 8 倍 | taper −1.1、bw 83.49→71.98 と崩壊 |
| 穂の剛性不足 | ヒンジ剛性 20 倍 | 3 倍で taper +1.9 だが払い finish −7.5 |

**「制御をどう強めても効かない」という共通点が答えを指していた。** 制御ではなく
接触モデルの問題（2.3）だった。

### 3.2 line_width の負債は「学習不足」ではなかった

追加学習で埋まらないので報酬設計を疑ったが、**46 字の天井と 2136 字の学習結果を
比べていた**のが誤り。層化標本 83 字で測り直すと方策はほぼ天井に達していた
（lw 天井 88.00 対 現行 86.99）。

**PPO の伸びしろがほぼ尽きている**というのがこの時点の正しい理解で、以降の改善は
学習ではなく計画側でしか得られない。

### 3.3 紙の位置の最適化（案 B）

`wrist_flex` の上余裕が 0.2° しかないので紙を近づければ余裕が生まれると考えたが、
**全条件で 0.1〜0.6° のまま**。近づけると elbow_flex が代わりに潰れ、175mm では
完筆 0%。持ち上げると完筆 0%。

| 紙 x | wrist_flex 上余裕 | elbow_flex 上余裕 | 完筆 |
|---:|---:|---:|---:|
| **235（現状）** | 0.2° | **9.7°** | **94%** |
| 215 | 0.1° | 1.1° | 83% |
| 195 | 0.6° | 0.1° | 83% |
| 175 | 0.6° | 0.1° | 0% |

**本当の制約は書き枠 110×197mm の大きさ**だった。この腕はどこに紙を置いても
手首を伸ばし切る必要がある。

### 3.4 収筆 3 拍・筆圧ゲート

「押してから戻す」を離散動作にすると止め finish が **−15.5**。現行の滑らかな
回鋒が 92-93 で全技法中最高だった。筆圧ゲートも全条件で悪化。

## 4. 事故の記録

**同じ症状を 3 回起こした。** いずれも紙を可動ボディにしたことが遠因。

| 回 | 症状 | 検出できなかった理由 |
|---|---|---|
| 1 | 学習ワーカーがメモリ枯渇で死亡、親が 6.5 時間無言待機 | 「プロセスが生きているか」しか見ていなかった |
| 2 | 学習の最終評価フェーズで落ちる | 同上 |
| 3 | 評価 4 プロセスが CPU 95% で 1 時間 45 分無限ループ | 環境にステップ上限が無い |

加えて `--batch-size must divide --n-steps * --n-envs` で起動直後に落ちたのを
17 分見逃した。**起動確認をログの `training start` で済ませていたが、あの行は
学習コマンドを呼ぶ前に出力される**ので成否と無関係だった。

**対策:**
- 監視は `progress.json` が**実際に前進しているか**で行う
- 評価に 40000 ステップの安全弁を追加（最長の鬱でも 9027 歩）
- 紙は固定に戻す（可動版は git 履歴に残す）

## 5. 追加した機能

### 5.1 複数文字レイアウト（`trajectory/layout.py`）

1 枚 1 字・大きさ固定（A4 で 11-12cm）だったのを桝目配置に。**字数で大きさが
自動的に変わる。** 既定は縦書き（上から下、右列から左列）。

| 字数 | 一字の枠 |
|---|---|
| 1 | 88×158mm |
| 4 | 88×39mm |
| 9（3×3） | 29×53mm |

### 5.2 画像から書く（`trajectory/image_layout.py`）

外部 OCR は未導入なので、お手本用のフォント字形マスクをテンプレートに照合する。
書体差に耐えるよう IoU / ブロック平均 / 布白の数 / 投影 / 重心を重ねた。

3 字（山川田）で切り出しは完璧、川と田は正解。**山は出と差 0.021 まで詰めたが
逆転しない**（「下に一画足しただけ」の関係で書体差に埋もれる）。候補を絞れば実用。

**線幅 11mm に対し字が 24-30mm になると布白が潰れる。** 13mm の筆で 24mm の字は
原理的に書けない。実機なら小筆に持ち替える場面。
→ `2026-08-21-image-to-calligraphy.md`

## 6. 実機投入の評価

**いまのままでは書けない。** 実機コードは一行も無く、ドメインランダム化も無効。

観測 371 次元のうち実機で取れないのは 16 次元（たわみ・墨の残量・穂の曲がり速度・
末端軸）。ただし**方策はそれらをほとんど使っていない**:

| 条件 | beauty | glyph | lw | bw | 完筆 |
|---|---:|---:|---:|---:|---:|
| 全観測 | 87.55 | 67.64 | 92.29 | 86.77 | 100% |
| たわみ・墨を 0 に | 87.66 | 67.84 | 92.35 | 86.90 | 100% |
| ＋筆圧に推定誤差 | 87.66 | 67.85 | 92.36 | 86.88 | 100% |

**ボトルネックは「筆圧をどう得るか」の一点**だった。位置制御サーボの追従誤差は
負荷トルクに比例するので、**センサなしで推定できる**:

| 使う情報 | R² |
|---|---:|
| 追従誤差のみ | 0.489 |
| ＋関節速度 | 0.707 |
| **＋筆先高さ** | **0.926** |
| ＋誤差変化と交差項 | **0.972** |

**未知の字でも R²=0.968、平均誤差 0.020**（筆圧の範囲 0-1.06 に対し 2%）。
追加ハードは不要。

**残る障壁はドメインランダム化。** 単一の物理パラメータでしか学習しておらず、
実機の摩擦・遅延・個体差に耐性がない。

## 7. 筆傾斜機構（ハードウェア）

起筆の三角形は**このハードでは作れない**と結論した。傾きを変える 3 関節はどれも
穂先を 17mm 以上動かし、`wrist_roll` は傾きに寄与しない（0.00°/0.1rad）。

**「グリッパー用サーボを転用すればいい」という指摘から設計が始まった。**

### 7.1 分かったこと

- 筆は `wrist_roll_link` に剛体で直付けされており、グリッパーの顎は筆に一切
  関与していない。**サーボは完全に空いている**
- グリッパー軸は z（紙面法線と同じ）なのでそのままでは左右に振るだけ。
  **手首を 90° ロールすると軸が y に向き、傾斜軸になる**
- シミュレータで実証: ロール 90° + グリッパー 0.80rad で傾き **+45.8°**

### 7.2 実物 STEP で判明した制約

設計書の仮値はほぼ全項目が違った。

| 項目 | 仮値 | 実測 |
|---|---|---|
| カウンタ支持 | 自作ピン＋軸受け | **不要**（純正が両持ち） |
| 内側クリア | 16.4mm | 33.4mm |
| ネジ | M2 皿×4 | M3 キャップ |
| `pivot_lateral` 下限 | 16mm | **下限なし**（別平面） |
| 天井 | 言及なし | **前腕が z≈28 で横切る** |
| 筆の全長 | 言及なし | **56mm が上限** |

**「前腕の天井」と「筆を切る必要がある」は、実物の STEP を読まなければ絶対に
出てこなかった。**

### 7.3 最終構成

```
pivot_to_tip 30 / 決定角 15° / yoke_index 0° / 固定顎は残す
lateral 7.765  axial 28.978  掴み代 16mm  筆全長 56mm
穂先移動 22.96mm（上限 23mm）  印刷部品 12.3g
wrist_flex 追加要求 0°
```

グリッパー軸は Wrist_Roll_Follower 座標系で **x=20.077 / z=24.350、Y 軸方向**。

長い軸が入らないのは制約に見えるが、**長い柄は人間の手のためにある**。ロボットは
軸をクランプで掴むので握りは要らない。56mm でも書字性能に影響はなく、慣性が
50 分の 1 になる分むしろ有利。

## 8. 残課題

1. **ドメインランダム化を入れた学習** — 実機投入の最後の大きなピース
2. **`entry_lean` の有効化** — 機構ができたら初めて機能する
3. **glyph_shape 62 / IoU 59** — 字形のズレは依然として最大の弱点
4. **line_width の負債 −1.29** — 天井に達しており学習では埋まらない
5. **紙の可動化のやり直し** — 接触パラメータを詰めてから
6. **穂の長さと軸径の実測** — 現在 22mm / φ7 はモデルの仮定であって実測値ではない
